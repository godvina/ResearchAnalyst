# Requirements Document

## Introduction

AI Level Summaries adds generative AI insight panels at each level of the Pattern Library's 5-level drill-down (Domain → Typology → Method → Signature → Precedent Case). When an analyst navigates to any level, the system displays a contextual summary generated by Amazon Bedrock (Claude Haiku), providing analytical narrative about the patterns, their relationships, and evidentiary strength. Summaries are cached in Aurora PostgreSQL to avoid redundant Bedrock invocations on repeated views.

## Glossary

- **Summary_Service**: The backend service (Lambda API handler) responsible for generating, caching, and serving AI summaries for each taxonomy level
- **Summary_Cache**: The Aurora PostgreSQL table (`ai_level_summaries`) that stores previously generated summaries with their associated taxonomy context keys
- **Pattern_Library_UI**: The frontend page (`pattern-library.html`) that renders the 5-level drill-down and displays AI insight panels
- **Bedrock_Client**: The boto3 client used to invoke Amazon Bedrock's Claude Haiku model for summary generation
- **Taxonomy_Level**: One of the five hierarchical levels in the pattern library: Domain, Typology, Method, Signature, or Precedent Case
- **Context_Key**: A composite identifier that uniquely identifies a taxonomy node (e.g., `crime/antitrust/bid_rotation` for a method-level summary)
- **TTL**: Time-to-live duration after which a cached summary is considered stale and eligible for regeneration
- **Taxonomy_Context**: The structured data (signatures, indicators, methods, precedent cases) gathered from the taxonomy JSON and OpenSearch to build a Bedrock prompt

## Requirements

### Requirement 1: Summary Generation via Bedrock

**User Story:** As a research analyst, I want AI-generated insight summaries at each drill-down level, so that I can quickly understand the significance and relationships of patterns without manually reviewing every signature.

#### Acceptance Criteria

1. WHEN an analyst navigates to a Taxonomy_Level, THE Summary_Service SHALL generate a natural-language summary of no more than 300 words by invoking the Bedrock_Client with the Taxonomy_Context for that level and SHALL return the summary to the requesting client within 10 seconds of the navigation event
2. WHEN generating a Domain-level summary, THE Summary_Service SHALL include the number of typologies, total signature count, and cross-typology relationship highlights in the prompt context
3. WHEN generating a Typology-level summary, THE Summary_Service SHALL include the method names, signature counts per method, severity distribution, and key precedent cases in the prompt context
4. WHEN generating a Method-level summary, THE Summary_Service SHALL include all signature descriptions, indicator lists, and precedent cases for that method in the prompt context
5. WHEN generating a Signature-level summary, THE Summary_Service SHALL include the signature's vector text, all indicators, precedent case details, and severity rating in the prompt context
6. WHEN generating a Precedent-Case-level summary, THE Summary_Service SHALL include the case name, related signatures that reference the case, and the evidentiary pattern it establishes in the prompt context
7. THE Summary_Service SHALL use the model `anthropic.claude-3-haiku-20240307-v1:0` for all summary generation
8. IF the Bedrock_Client invocation fails or does not respond within 10 seconds, THEN THE Summary_Service SHALL return an error indication to the analyst stating that summary generation is unavailable and SHALL preserve the analyst's current navigation state without data loss
9. IF the Taxonomy_Context for a given level contains no signatures or child elements, THEN THE Summary_Service SHALL return a message indicating that insufficient data is available to generate a summary for that level

### Requirement 2: Summary Caching in Aurora

**User Story:** As a system operator, I want generated summaries cached in Aurora, so that repeated views of the same taxonomy level return instantly without re-invoking Bedrock.

#### Acceptance Criteria

1. WHEN the Summary_Service generates a summary, THE Summary_Service SHALL store the result in the Summary_Cache table keyed by Context_Key and set the expires_at field to the current timestamp plus the configured TTL
2. WHEN a cached summary exists for a requested Context_Key and the current timestamp is before the cached entry's expires_at value, THE Summary_Service SHALL return the cached summary without invoking the Bedrock_Client within 200 milliseconds of receiving the request
3. IF a cached summary exists for a requested Context_Key but the current timestamp is at or past the cached entry's expires_at value, THEN THE Summary_Service SHALL treat the request as a cache miss, invoke the Bedrock_Client to generate a new summary, and replace the expired cache entry
4. THE Summary_Cache SHALL store the following fields: context_key (maximum 512 characters), taxonomy_level, summary_text (maximum 50,000 characters), model_id, prompt_token_count, completion_token_count, generated_at (UTC timestamp), and expires_at (UTC timestamp)
5. WHEN taxonomy data changes for a given Context_Key (a signature is added, modified, or removed under that key's taxonomy path), THE Summary_Service SHALL mark all cached summaries whose context_key shares the same taxonomy path as stale by setting their expires_at to the current timestamp
6. THE Summary_Service SHALL use a default TTL of 7 days for cached summaries
7. IF the Summary_Service fails to write a generated summary to the Summary_Cache, THEN THE Summary_Service SHALL still return the generated summary to the caller and log the cache write failure

### Requirement 3: API Endpoint for Summary Retrieval

**User Story:** As the Pattern_Library_UI, I want a REST endpoint to request summaries by taxonomy level and context, so that the frontend can display AI insights without directly invoking Bedrock.

#### Acceptance Criteria

1. THE Summary_Service SHALL expose a GET endpoint at `/pattern-library/summary/{level}/{context_key}` that accepts `level` as one of the defined taxonomy levels (e.g., domain, typology, method, signature, precedent_case) and `context_key` as a non-empty string of at most 256 characters, and returns the summary for the specified taxonomy node
2. WHEN a GET request is received with a valid level and context_key, THE Summary_Service SHALL return a 200 JSON response containing: summary_text (string, at most 5000 characters), generated_at (ISO 8601 timestamp), is_cached (boolean), and taxonomy_level (string matching the requested level)
3. WHEN a GET request is received with an unrecognized context_key for a valid level, THE Summary_Service SHALL return a 404 response with error code `SUMMARY_NOT_FOUND`
4. IF a GET request is received with an invalid or unrecognized level value, THEN THE Summary_Service SHALL return a 400 response with error code `INVALID_TAXONOMY_LEVEL` indicating the accepted level values
5. WHEN the Bedrock_Client invocation fails during summary generation, THE Summary_Service SHALL return a 503 response with error code `GENERATION_FAILED` and a human-readable message indicating the generation service is unavailable
6. THE Summary_Service SHALL respond within 500ms at the 95th percentile for cached summaries
7. THE Summary_Service SHALL respond within 15 seconds at the 95th percentile for uncached summaries requiring Bedrock generation

### Requirement 4: Frontend AI Insight Panel

**User Story:** As a research analyst, I want to see a visually distinct AI insight panel at the top of each drill-down view, so that the AI summary is immediately visible when I navigate to a new level.

#### Acceptance Criteria

1. WHEN a drill-down level is rendered, THE Pattern_Library_UI SHALL display an AI insight panel positioned above the level's main content area
2. WHILE the summary is being fetched from the Summary_Service, THE Pattern_Library_UI SHALL display a loading skeleton animation within the AI insight panel
3. WHEN the summary response arrives, THE Pattern_Library_UI SHALL replace the loading skeleton with the rendered summary text, truncated to a maximum of 500 characters with an expand control if the full text exceeds that length
4. THE Pattern_Library_UI SHALL display a "🤖 AI Insight" label and a text-based status indicator reading either "Cached" or "Generated" to show the source of the summary
5. IF the Summary_Service returns an error, THEN THE Pattern_Library_UI SHALL display a dismissible error message indicating the summary could not be loaded, and SHALL continue showing the taxonomy content without the summary panel content
6. WHEN the user activates the refresh button, THE Pattern_Library_UI SHALL disable the refresh button, bypass the cache, and request a new summary from the Summary_Service; the button SHALL remain disabled until the new response or error is received

### Requirement 5: Prompt Construction and Quality

**User Story:** As a research analyst, I want summaries that are concise, analytically useful, and grounded in the actual taxonomy data, so that the AI insights add genuine value to my investigation workflow.

#### Acceptance Criteria

1. THE Summary_Service SHALL construct prompts that instruct the model to produce summaries between 2 and 5 sentences in length
2. THE Summary_Service SHALL include a system prompt instructing the model to act as an investigative intelligence analyst providing pattern-based insights
3. THE Summary_Service SHALL include only taxonomy data from the requested level and one level below in the prompt context to bound token usage
4. THE Summary_Service SHALL set max_tokens to 300 for all summary generation requests
5. IF the prompt context exceeds 4000 tokens, THEN THE Summary_Service SHALL truncate signatures in ascending severity order (Low, then Medium, then High, then Critical) until the prompt context is at or below 4000 tokens
6. IF the prompt context still exceeds 4000 tokens after all signatures have been truncated, THEN THE Summary_Service SHALL truncate precedent case details in chronological order (oldest first) until the prompt context is at or below 4000 tokens
7. IF the Bedrock_Client returns a summary that exceeds 5 sentences, THEN THE Summary_Service SHALL return only the first 5 sentences of the generated summary

### Requirement 6: Cache Invalidation on Taxonomy Update

**User Story:** As a system operator, I want cached summaries to be invalidated when the underlying taxonomy data changes, so that analysts always see summaries reflecting the current pattern library.

#### Acceptance Criteria

1. WHEN the `typology-patterns` OpenSearch index is re-seeded via `index_pattern_library.py`, THE Summary_Service SHALL mark all cached summaries as stale within 5 seconds of the re-seed operation completing
2. WHEN a single signature is added or modified, THE Summary_Service SHALL mark as stale only the summaries in the direct ancestor chain of the affected signature (the parent Method, the parent Typology, and the parent Domain)
3. THE Summary_Service SHALL expose a POST endpoint at `/pattern-library/summary/invalidate` that accepts an optional `context_key` parameter (maximum 256 characters) and SHALL return an HTTP 200 response including the count of summaries invalidated; IF no `context_key` is provided, THEN THE Summary_Service SHALL invalidate all cached summaries
4. WHEN invalidation is triggered, THE Summary_Service SHALL NOT delete the stale summaries but SHALL serve them with an `is_stale: true` flag until the summary is regenerated on the next request for that summary
5. IF the `/pattern-library/summary/invalidate` endpoint receives a `context_key` that does not match any cached summary, THEN THE Summary_Service SHALL return an HTTP 200 response with an invalidated count of 0

### Requirement 7: Cost and Rate Controls

**User Story:** As a system operator, I want safeguards against excessive Bedrock invocations, so that the demo stays within budget even under heavy browsing.

#### Acceptance Criteria

1. THE Summary_Service SHALL enforce a maximum of 60 Bedrock invocations per fixed clock-hour window (resetting at minute :00) across all taxonomy levels
2. IF the hourly rate limit is reached and a cached summary exists that is no older than 24 hours, THEN THE Summary_Service SHALL return that cached summary with an `is_throttled: true` flag instead of invoking Bedrock
3. IF the hourly rate limit is reached and no cached summary younger than 24 hours exists, THEN THE Summary_Service SHALL return a 429 response with error code `RATE_LIMITED` and a `retry-after` header set to the number of seconds remaining until the next clock-hour boundary
4. THE Summary_Service SHALL log each Bedrock invocation with the context_key, token counts, and latency to CloudWatch for cost monitoring
5. WHEN a new clock-hour begins, THE Summary_Service SHALL reset the invocation counter to zero
